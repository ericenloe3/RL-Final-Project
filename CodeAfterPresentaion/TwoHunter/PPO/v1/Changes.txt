How the parameter-sharing was implemented for PPO
The interesting design challenge was making one shared hunter network work with PPO's on-policy rollouts. SAC's replay buffer trivially accepts pooled transitions — push h1 and h2 transitions into the same buffer and sample uniformly. PPO doesn't have that flexibility because rollouts are structured: each "trajectory slot" must be a coherent sequence for GAE to work correctly.
The solution is to give the hunter rollout buffer 2 * NUM_ENVS slots instead of NUM_ENVS. Slots 0..N-1 hold hunter1's transitions across the parallel envs; slots N..2N-1 hold hunter2's transitions. Within any one slot, transitions form a coherent single-agent trajectory in one environment, so the standard GAE recursion runs unchanged. Done flags are duplicated across the paired slots since both hunters share episode boundaries.
The network query is the elegant part: at each env step, we stack h1 and h2 observations into one batched input of shape (2*NUM_ENVS, obs_dim) and run a single forward pass through policies["hunter"]. The output is split back into h_acts[:N] for hunter1 and h_acts[N:] for hunter2. Crucially, both halves go through exactly the same weight matrices — there's one network used twice per env step. During PPO updates, gradients from both hunters' losses accumulate into the same parameters, so the two hunters genuinely co-train.
This gives the hunter network 2× the gradient data per environment step compared to the prey network, mirroring the same data asymmetry SAC achieves through its shared replay buffer.
Hyperparameter changes
HIDDEN["hunter"]: 128 → 192. The single significant change relative to PPO 1v1 v7. In 1v1 the hunter task was simpler than the prey task (track one visible target vs avoid obstacles + seek cover + manage corners), so 128 was sufficient. In 2v1 the shared hunter network must encode coordination — patterns like "if my teammate is on the prey's left, I should approach from the right." That's genuinely more complex than 1v1 pursuit, so matching the prey's 192 capacity gives room for the coordination logic to fit.
Curriculum: speed ramp removed, obstacle ramp kept. The 1v1 curriculum ramped hunter speed from 4.0 to 4.5 to introduce the speed advantage gradually. In 2v1 speeds are constant at 4.5/4.5 (env-level fairness change), so only obstacle density varies across phases. The phases are (0%, 0 obstacles), (15%, 1-3 obstacles), (40%, 3-6 obstacles).
Hyperparameters intentionally kept the same
These choices were already correct for the algorithm regardless of agent count, so I didn't touch them:
log_std clamp [-3, +0.5]. The v7 fix that prevented the prey entropy explosion. Just as relevant in 2v1 — actually more so, because the prey faces a harder environment and is more likely to fall into the same losing-equilibrium-with-runaway-entropy trap. The *SAT* saturation marker in the per-update logs lets you spot it immediately if it happens.
ENT_COEF: hunter 0.02 → 0.003, prey 0.05 → 0.005. The asymmetric annealing schedule reflects the prey's harder credit-assignment problem, which is even more pronounced in 2v1 — the prey has more agents to track and longer chains of cause-and-effect to reason about. If anything, the prey might benefit from slightly higher exploration here, but I kept the schedule identical to maintain comparability with the 1v1 results.
PPO_EPOCHS: hunter 3, prey 8. Same reasoning. The 2.7× ratio is about the relative difficulty of the gradient signal, not the number of hunters. Since the shared hunter network sees 2× the data per step (from two hunters), giving it only 3 epochs per batch is actually appropriate — more epochs on already-doubled data could destabilise.
HUNTER_FREEZE_FRAC = 0.20. PPO is on-policy, so the freeze period doesn't poison a long-lived buffer the way it does for SAC. SAC had to drop to 5% because frozen transitions polluted the replay buffer. PPO keeps the full 20% freeze and gives the prey a substantial head start before facing trained hunters. During the freeze, both h1 and h2 emit uniform-random actions, but the prey trains normally — the hunter rollout buffer still gets populated (with random-action transitions) but those are discarded after the next update, so there's no lasting damage.
Comparison to SAC 2v1 design
The two implementations differ only where the algorithms differ:

Network capacity: PPO 192/192 (same as SAC 192/192).
Freeze duration: PPO 20% / SAC 5%. This is the most visible asymmetry, driven by buffer poisoning concerns.
Hunter data multiplier: Both achieve 2× via different mechanisms — PPO via doubled rollout slots, SAC via doubled buffer pushes per env step.
Capture credit: Both share the capture reward between h1 and h2.
Coordination encoding: Both rely on parameter sharing rather than explicit communication channels.

Diagnostic logging additions
Per-update logs now include capture_h1 and capture_h2 separately so you can see if the parameter sharing is actually producing two contributing hunters or if one hunter is dominating captures. Per-agent returns (hunter1_avg_return, hunter2_avg_return, prey_avg_return) let you spot if the two hunters are diverging despite sharing a network — which would suggest the asymmetric position-in-observation is causing different gradient signals to win.
The log_std_raw and log_std_clamped saturation markers from PPO v7 are still in place. If the prey's log_std_raw pins at +0.5 for many consecutive logs, you'll see *SAT* in the console and know the entropy regulation is fighting the gradient — same diagnostic that uncovered the entropy explosion in 1v1.
